# AI Cartoon Video PoC (100% local)

Generates a short Hindi cartoon narration video fully on-device:

```
story.txt -> local LLM (scene breakdown) -> local Stable Diffusion (cartoon images)
          -> local Hindi TTS -> ffmpeg zoom/pan animation -> subtitles -> final_video.mp4
```

No cloud APIs, no frontend, no backend server, no database, no Docker.

**Status: working end-to-end.** `python main.py --story input/story.txt` produces a real,
inspected 30-second Hindi cartoon video. See `output/latest/final/final_video.mp4`.

## Hardware this was built/tested on

- CPU: AMD Ryzen 7 3700X (8c/16t)
- RAM: 64 GB
- GPU: NVIDIA GeForce RTX 2060, **6 GB VRAM** (confirmed via `nvidia-smi`; the user initially
  described it as 8GB, but the card actually reports 6144 MiB total)
- OS: Windows 10/11, FFmpeg available via choco install (NVENC-capable build)

Given 6GB VRAM, the model choices below were picked to comfortably fit with headroom,
rather than the largest models available.

## Model choices and why

| Stage | Model | Why |
|---|---|---|
| Scene breakdown (LLM) | `Qwen/Qwen2.5-3B-Instruct` (transformers, **CPU**, float32) | Originally planned as a GGUF model via `llama-cpp-python`, but that package failed to build locally (needs MSVC/nmake, not installed). Switched to the safetensors checkpoint via `transformers` (no compiler needed). Tried 1.5B first - it repeatedly mistranslated the Hindi story (turned "बिल्ली"/cat into "girl" or "cow"); 3B gives much more reliable Hindi comprehension. Kept on CPU deliberately: at 3B params, fp16-on-GPU would compete with image generation for the 6GB VRAM budget right after; CPU with 64GB RAM available is the safer trade-off since this stage runs once per video and correctness matters more than its ~90-100s runtime |
| Cartoon images | `nitrosocke/mo-di-diffusion` (SD1.5-based, GPU fp16) | SD1.5-class models run comfortably in ~3-4GB VRAM at 512x512 on a 6GB card; this checkpoint is finetuned for a modern cartoon/Disney look (no SDXL/Flux - those need 8GB+ to run reliably). ~5s/image on the RTX 2060 |
| Hindi narration (TTS) | `facebook/mms-tts-hin` (VITS) | Lightweight (~150MB), GPU or CPU, officially supports Hindi, single consistent narrator voice, fast (<1s/sentence) and reliable. More natural/expressive alternatives (e.g. Coqui XTTS-v2) exist but are heavier and were out of scope for this first PoC pass |
| Animation | ffmpeg `zoompan` filter | No extra model needed; applies subtle zoom-in/zoom-out/pan-left/pan-right motion per scene plus short fades, so it reads as more than a slideshow |
| Subtitles | plain SRT + ffmpeg `subtitles` filter (burned in) | Uses the Windows-bundled "Nirmala UI" font, which renders Devanagari (Hindi) correctly |

Models are downloaded once (first run) into `F:/ai-models-cache` (kept off the small `A:`
project drive, which only has ~14GB free) and reused on every subsequent run.

## Real problems hit during development (and fixes)

This was actually built and iterated against real failures, not just coded blind:

1. **Project's default Python was 3.14** - too new, no PyTorch/diffusers wheels available.
   Fixed by provisioning Python 3.11.14 via `uv` for a dedicated venv.
2. **`llama-cpp-python` failed to build** (`CMake Error: CMAKE_C_COMPILER not set` - no MSVC
   build tools installed). Switched the LLM stage to plain `transformers` instead of GGUF.
3. **Hugging Face's "Xet" CDN backend stalled indefinitely** on every multi-GB file download
   (confirmed with a raw `curl` bypass, not just the Python client) while small files and an
   older classic-CDN path worked fine. Fixed by forcing `HF_HUB_DISABLE_XET=1` globally in
   `src/config.py`.
4. **1.5B LLM mistranslated the story's character species** (बिल्ली/cat → "girl", then on a
   retry → "cow") - likely pattern-matching "milk shop" stories from training data over the
   actual Hindi word. Fixed two ways: (a) upgraded to 3B for better Hindi comprehension, and
   (b) added a small deterministic Hindi→English animal-noun dictionary
   (`detect_character_species` in `src/story.py`) so the species itself is never left to the
   LLM's translation when a common word is recognized - only extra visual traits (color,
   accessories) are generated by the model.
5. **First full image batch had serious defects**: one scene rendered 3 cats instead of 1,
   one scene degenerated into a repeating wallpaper-like pattern (not a coherent image at
   all), and one scene showed a human girl as the main subject with the cat shrunk into the
   background - because prompts mentioned "shopkeeper" and an untranslated "billi", giving
   Stable Diffusion a second character to render. Fixed by: stripping any leftover Hindi
   words/other-character mentions from LLM-generated visual prompts
   (`_sanitize_visual_prompt`), instructing the LLM to describe only the main character's own
   action/pose, prepending `solo, single {species}, only one {species}` to every image prompt,
   and expanding the negative prompt to discourage patterns/tiling/multiple subjects/humans.
   Re-ran and visually confirmed all 5 images now show one consistent cat.
6. **Video came out short** (23.8s vs the 30s target) because real Hindi TTS speech is faster
   than the LLM's guessed per-scene duration. Fixed by computing actual padding per scene from
   `(target_duration - total_narration) / scene_count` (clamped 0.3-2.5s) instead of a flat
   0.4s gap, so the final video lands on the requested duration.
7. `enable_vae_slicing()` doesn't exist on this diffusers version's `StableDiffusionPipeline`
   - removed (attention slicing alone is sufficient for VRAM headroom on 6GB).
8. **The pan animation (2 of 5 scenes) was completely static** - user caught this by actually
   watching the video, not something the earlier automated checks surfaced. Root cause: this
   exact ffmpeg build's (`7.1-essentials` from gyan.dev) `zoompan` filter has non-functional
   `x`/`y` parameters - verified with 6+ isolated tests (constant values, `on`-based formulas,
   self-referencing formulas, even combined with a simultaneously-changing zoom) and every one
   produced pixel-identical frames; only `zoompan`'s `zoom` parameter itself actually animates.
   Fixed by rewriting pan motions to use the `crop` filter with time (`t`)-based `x`/`y`
   expressions instead (a different, unaffected code path) - verified with a numeric pixel-diff
   (87-89% of pixels changed between frames, vs. 0% before). Zoom motions still use `zoompan`
   (its `zoom` parameter does work).
9. **Final video looked soft/blurry compared to the source images** - ffmpeg's default scale
   algorithm is bilinear, which blurs noticeably when upscaling 512px source art by ~2x for the
   zoom/pan canvas. Fixed by switching to `flags=lanczos` plus a mild `unsharp` pass in the
   animation filter chain - confirmed visually much closer to source sharpness.

## Setup

```powershell
# one-time: create venv with Python 3.11 (ML libs need <=3.12; project default was 3.14)
uv venv --python 3.11.14 F:/ai-cartoon-poc-venv

# install torch with CUDA 12.4 wheels (matches RTX 2060 / driver, backward compatible)
uv pip install --python F:/ai-cartoon-poc-venv/Scripts/python.exe torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu124

# install the rest
uv pip install --python F:/ai-cartoon-poc-venv/Scripts/python.exe -r requirements.txt
```

## Run

```powershell
F:/ai-cartoon-poc-venv/Scripts/python.exe main.py --story input/story.txt --duration 30 --scenes 6
```

First run downloads ~7GB of model weights (3B LLM + SD1.5 checkpoint + TTS model) into
`F:/ai-models-cache`; subsequent runs reuse the cache and are much faster.

## Output

Every run creates a fully independent, timestamped folder — nothing is ever overwritten:

```
output/run-YYYYMMDD-HHMMSS/
├── input/story.txt
├── scenes/scenes.json, characters.json, visual_prompts.json
├── images/scene_001.png ... scene_005.png
├── audio/scene_001.wav ... + narration.json
├── animation/scene_001.mp4 ...        (silent, per-scene zoom/pan clips)
├── subtitles/subtitles.srt
├── final/final_video.mp4
├── logs/process.log
└── report.json
```

`output/latest/` is overwritten after every **successful** run with a copy of that run's
full output, for quick access. Failed runs still produce a `report.json` with
`"status": "failed"` and the error, but do not touch `output/latest/`.

## Actual measured performance (RTX 2060 6GB, Ryzen 7 3700X)

From a real run (`output/run-20261004-120416/report.json`), 5-scene / 30s video:

| Stage | Time |
|---|---|
| Scene generation (LLM, CPU) | ~104s |
| Image generation (5 images, GPU) | ~28s (~5.6s/image) |
| Hindi TTS (5 clips) | ~3s |
| Animation (ffmpeg zoompan, 5 clips) | ~3s |
| FFmpeg concat/mux/subtitles | ~2s |
| **Total** | **~140s** (first run after models are cached; add several more minutes for the one-time ~7GB download) |

The LLM stage dominates total time since it runs on CPU by design (see point 4 above).

## Real character motion (`--animation-mode ai`) and running it on AWS EC2

By default (`--animation-mode camera`, no flag needed) animation is ffmpeg zoom/pan over
still images - works fine on the 6GB RTX 2060 above. There's also an opt-in
`--animation-mode ai` mode (`src/ai_animation.py`) that uses **AnimateDiff**
(`guoyww/animatediff-motion-adapter-v1-5-2`) on top of the same `mo-di-diffusion` SD1.5
checkpoint to generate actual character/object motion (walking, reacting, etc.) instead of
just panning a static image. This needs much more VRAM and time than the 6GB dev machine
comfortably has, so it's meant to be run on a rented GPU - still 100% local/open-source
inference, just on bigger rented hardware instead of a laptop GPU (not a cloud AI API call).

**Bug fixed during local testing** (documented here because it's non-obvious and will bite
you again if you ever bump dependency versions): `guoyww/animatediff-motion-adapter-v1-5-2`'s
`"fp16"` variant file on the Hugging Face Hub is mislabeled - it actually contains fp32 data
internally. Loading it via `MotionAdapter.from_pretrained(..., variant="fp16")` silently
produces a corrupted model that generates pure brown/grey noise video with **no error, no
warning, no crash** - it looks like a successful run until you actually look at the frames.
Found by bisecting through 7 isolated tests (ruling out scheduler config, VAE fp16 precision,
`enable_model_cpu_offload`, and checkpoint choice - both `mo-di-diffusion` and the literal
base `runwayml/stable-diffusion-v1-5` the adapter was trained against all produced identical
noise) down to this one flag. Fix: `src/ai_animation.py` loads the adapter **without**
`variant="fp16"` and lets `torch_dtype=torch.float16` do the cast instead - verified with
real frame extraction afterward (coherent cartoon cat, visibly changing pose across frames,
not noise).

### Step-by-step: running `--animation-mode ai` on an AWS EC2 GPU instance

1. **AWS account**: sign up at aws.amazon.com if you don't have one (needs a card on file).
   New accounts sometimes need a support-ticket "service quota increase" for GPU instances
   before you're allowed to launch one (`EC2 > Service Quotas > Running On-Demand G and VT
   instances` - request e.g. 4 vCPUs if it's currently 0). This can take a few hours to a day
   to approve, so do it first if you've never launched a GPU instance on this account before.

2. **Pick an instance type**:

   | Instance | GPU | VRAM | ~On-demand $/hr (us-east-1) | Verdict |
   |---|---|---|---|---|
   | `g4dn.xlarge` | NVIDIA T4 | 16 GB | ~$0.53 | **Recommended** - plenty of headroom for AnimateDiff at 512x512, cheapest GPU option |
   | `g5.xlarge` | NVIDIA A10G | 24 GB | ~$1.01 | Faster, more headroom if you raise resolution/frame count later; costs ~2x |
   | `g4dn.2xlarge` | NVIDIA T4 | 16 GB | ~$0.75 | Same GPU as xlarge, more vCPU/RAM - only worth it if the LLM (CPU) stage feels slow |

   Prices change and vary by region - check the [EC2 pricing page](https://aws.amazon.com/ec2/pricing/on-demand/)
   for current numbers before launching. `g4dn.xlarge` is the right default for this project.

3. **Launch the instance** (EC2 console → Launch Instance):
   - **AMI**: search for "Deep Learning AMI" (the official AWS one, e.g. "Deep Learning Base
     OSS Nvidia Driver GPU AMI (Ubuntu 22.04)"). This comes with the NVIDIA driver and CUDA
     already installed - skips the most error-prone manual setup step.
   - **Instance type**: `g4dn.xlarge` (from above).
   - **Key pair**: create a new one, download the `.pem` file, keep it safe - needed for SSH.
   - **Storage**: bump the root volume to **100 GB** (default is often 45-75GB; the AMI itself
     is large, and model weights here total ~10-12GB, with extra working space for venvs/pip
     caches).
   - **Security group**: allow SSH (port 22) from "My IP" only (not 0.0.0.0/0, to keep the box
     private).
   - Launch, wait ~1-2 min for it to reach "Running".

4. **Connect via SSH**:
   ```bash
   chmod 400 your-key.pem
   ssh -i your-key.pem ubuntu@<instance-public-ip>   # public IP shown in EC2 console
   ```

5. **Verify the GPU is visible**:
   ```bash
   nvidia-smi   # should show the T4/A10G and driver version
   ```

6. **Get the project onto the instance** (pick one):
   ```bash
   # option A: if the project is in a git repo you control
   git clone <your-repo-url> ai-cartoon-video-poc

   # option B: copy from your Windows machine (run this on Windows, not the EC2 box)
   scp -i your-key.pem -r "a:\ai-video-lab\02-ai-cartoon-video-poc" ubuntu@<instance-ip>:~/ai-cartoon-video-poc
   ```

7. **Install dependencies** (Ubuntu + Deep Learning AMI already has Python3/CUDA):
   ```bash
   cd ~/ai-cartoon-video-poc
   sudo apt-get update && sudo apt-get install -y ffmpeg
   python3 -m venv .venv
   source .venv/bin/activate
   pip install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu124
   pip install -r requirements.txt
   ```

8. **Set the model cache location** (avoid re-downloading into the small root volume by
   accident, and keep the Xet-stall workaround from the Windows setup):
   ```bash
   export AI_CARTOON_MODEL_CACHE=~/ai-models-cache
   export HF_HUB_DISABLE_XET=1   # same CDN-stall workaround as local dev, cheap to keep
   ```

9. **Run the pipeline** with real AI motion:
   ```bash
   python main.py --story input/story.txt --duration 30 --scenes 6 --animation-mode ai
   ```
   First run downloads model weights (LLM + SD checkpoint + TTS + AnimateDiff adapter, ~12GB
   total) - expect several minutes depending on the instance's network speed. Each scene's
   AnimateDiff clip takes roughly 1-2 minutes on a T4 at the default settings
   (`AI_VIDEO_NUM_FRAMES=16`, `AI_VIDEO_STEPS=25`, 512x512 in `src/config.py`) - a 6-scene
   video should finish in well under 30 minutes total, a large step down from the 6GB laptop
   GPU where this mode isn't practical at all.

10. **Get the output back to your machine**:
    ```bash
    # run this on Windows, not the EC2 box
    scp -i your-key.pem -r ubuntu@<instance-ip>:~/ai-cartoon-video-poc/output/latest "a:\ai-video-lab\02-ai-cartoon-video-poc\output\ec2-latest"
    ```

11. **Stop or terminate the instance when done** - GPU instances bill by the hour whether or
    not you're actively using them. From the EC2 console: **Stop** keeps the disk (and
    downloaded model cache) for a later run but still bills for the storage; **Terminate**
    deletes everything and stops all billing. If you'll run this again soon, Stop is more
    convenient (skips re-downloading ~12GB of models); otherwise Terminate.

## Known PoC limitations (intentional, per spec)

- Character consistency is prompt-based only (same character description string + "solo,
  single X" framing + same seed injected into every scene's image prompt). No
  LoRA/IP-Adapter/ControlNet. Visually consistent in practice (white cat, red scarf, recurring
  art style) but not pixel-identical across scenes - expected for prompt-only consistency.
  Stable Diffusion also occasionally renders small ambiguous background shapes; not a blocker
  but a known SD1.5-class limitation.
- Some generated images show a faint repeating watermark-like artifact in busy background
  areas - a known quality issue with this particular scraped-data cartoon finetune.
- Animation is ffmpeg zoom/pan on still images, not true AI video generation.
- One single narrator voice for all dialogue/narration.
- No background music/SFX by default (out of scope per spec; optional local WAV mixing
  could be added later).
- Scene count is driven by the story's natural sentence count (capped at `--scenes`), so a
  5-sentence story yields 5 scenes, not a forced 6 - keeps narration verbatim and avoids
  mid-sentence splitting.
